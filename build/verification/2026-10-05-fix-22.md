# #22, the ports and SSH auth: what ran, and on which bytes

## The crash

The board went down a few seconds after logging in over SSH from kitty
(`kitten ssh`), with a bad pointer in a VMA tree in one case and garbage in
jffs2's node lists in another. Plain `ssh` never did it, which is why about
200 logins, 30 minutes of fork and network load and a debug kernel with SLUB
poisoning all came back clean.

A debug kernel that fills every new stack with a pattern and measures what is
left at exit found it: each hush subshell the kitten bootstrap started had 0
bytes of its 16 KiB stack left. On NOMMU, hush re-executes itself for a
subshell and passes every shell variable as an argument, and
`transfer_args_to_stack()` copies the arguments and environment to the top
of the stack without checking that they fit. The FDPIC loader sized the
stack only by the program's `PT_GNU_STACK`, so the copy ran past the bottom
and over whatever kernel memory was below.

Kernel patch 62 adds the size of the arguments and their vectors to the
stack. [`2026-10-05-fdpic-args.json`](2026-10-05-fdpic-args.json):

- A `sh` with a 30 KiB variable and one subshell, over SSH: the 0.9 kernel
  oopsed on the second run. With the patch, 20 runs of 30 KiB, 10 of 60 KiB
  and 5 of 120 KiB, `tainted` 0 after each.
- The kitten's 32 subshells kept at least 11044 of their 32768 bytes.
- MemAvailable a minute after boot, two boots each: 3764 and 3832 kB with the
  0.9 kernel, 3788 and 3788 kB with the patch.

## The build, and what was on the board

`build/reproduce.sh` built `62051c2` from scratch. Its kernel and rootfs were
written to the board's `linux` and `rootfs` partitions only, over an `/etc`
and `/home` already in use, and the suite read both back and matched their
hashes:

```
64082aa867915be54dcd041347a9e89e6b16ffb0ef6e27f5c48ea236ed51c61a  xipImage
22ade9e977f65727d51dba80d34e8201a1209b00575fc9f6b46ef22f13e67deb  rootfs.cramfs
4a8df83ca7c2aed19f7807f8b4375fcee779f295c1041274b437dcad1eefa27b  linux-esp32s3-native-full.bin
```

Bootloader, partition table, core 0 firmware and the factory `/home` are
byte-identical to 0.9's.

- **Board suite: 35/35**
  ([`2026-10-05-results.json`](2026-10-05-results.json)), MemAvailable
  4120 kB at the baseline and 4036 kB at the end.
- **Beyond the suite: 11/11**
  ([`2026-10-05-extra-tests.json`](2026-10-05-extra-tests.json)), including
  the new one: five subshells re-executed with 30 KiB of arguments, `tainted`
  0.
- **Ports and SSH auth from the host: 1/7 on these bytes.** `remote-login
  port` and `auth` did nothing once `/etc/remote-login.conf` existed: hush
  exits a `set -e` script when a `while read` loop reaches the end of its
  input, and bash, which the host tests ran under, does not. `a548715` reads
  the file with `sed`. With that `remote-login` and `ssh-server` bind-mounted
  over the rootfs copies, **7/7**
  ([`2026-10-05-network-services.json`](2026-10-05-network-services.json)):
  SSH on 2222, password and key, keys only, password only, Telnet on 2323,
  the web page on 8080, and the board's settings put back.

The host tests now run the board scripts under the image's hush as well
(`build/host-hush.sh`, `BOARD_SH`); under it, the old `remote-login` fails 7
of its 19 tests. A second clean build, of the commit with that fix, was
started and stopped before it finished, so no image of it was flashed.
