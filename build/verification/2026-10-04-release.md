# 0.9: the committed images, and what ran on them

The images in `images/` are a clean `./run.sh` build of `1110d53`, made in a
fresh clone of the release branch with its own work directory and downloads.
The sources it built differ from this commit only in documentation, the CI
workflow, the images and records added here, none of which reach the image.
The kernel is `v7.2.4-esp32s3.2` of
[linux-esp32s3](https://github.com/paulneja/linux-esp32s3): the tree the
build patched and compiled was compared file by file with that commit and
matches, apart from the repository's own README.

The bootloader, the partition table, the core 0 firmware and the factory
`/home` are byte-identical to 0.8.1's.

The Image workflow built the same sources twice more on GitHub's runners
(run 37180287494, on `b0e1a38`, which adds only the CI check for the two new
fork patches). Its two builds
([`2026-10-04-release-reproducibility.json`](2026-10-04-release-reproducibility.json)),
and its first build against these images
([`2026-10-04-release-vs-ci.json`](2026-10-04-release-vs-ci.json)), match
byte for byte in `bootloader.bin`, `partition-table.bin`,
`network_adapter.bin`, `xipImage` and `home.jffs2`. `etc.jffs2`,
`rootfs.cramfs` and the combined image differ in one file, `/etc/shadow`,
from the random salt of the default password, as in every release before.
The recorded configurations match too, except the job count in the
toolchain's, which does not reach the output.

## What was on the board

These exact bytes were flashed and tested: the combined image above, written
at `0x0` with `flash.sh --images`, on the same ESP32-S3 N16R8 used for every
earlier record.

- **Board suite: 36/36**
  ([`2026-10-04-results.json`](2026-10-04-results.json)), run by
  `./run.sh --all` in that clone, MemAvailable 4204 kB at the baseline.
- **Beyond the suite: 10/10**
  ([`2026-10-04-extra-tests.json`](2026-10-04-extra-tests.json)), `tainted` 0
  at the end. The slowest switch between forked processes was 5.0 ms.
- **Factory boots: 20 of 20 clean**, none inconclusive
  ([`2026-10-04-soak.json`](2026-10-04-soak.json)), login after 15.1 s on
  average. That bounds the fault rate at 14% or less at 95%, one-sided.
- **SSH with a PTY from the host over WiFi: pass**
  ([`2026-10-04-ssh-pty.json`](2026-10-04-ssh-pty.json)).
- **WiFi:** a wrong password reported as one in 20 s and a scan right after
  it working (#20), then 100 `ip link set espsta0 down/up` and 25
  `wifi connect` in a row. One `udhcpc` and one `wpa_supplicant` at the end,
  `tainted` 0, nothing in `dmesg`.
- **fork through the MMU:** with `fork_bank_mmu` off, on and off again, the
  slowest switch under three busy Bash processes was 29.3 ms copying against
  5.2 and 5.6 ms through the MMU; under four MicroPython processes holding
  192 KiB each, 33.5 ms against 9.3 and 9.6 ms
  ([`2026-10-04-fork-mmu.json`](2026-10-04-fork-mmu.json)). A Bash holding
  716 KiB to 1.3 MB of private memory forked three children each time.
- **First login:** after the tests put the factory login back, `changeme123`
  is accepted and a new password is asked for before anything else, and
  ports 22 and 23 are closed.

WiFi setup over Bluetooth from a phone, and an update from 0.8.1 with
`flash.sh --parts` that kept the password and the WiFi, passed on an earlier
build with the same kernel (`2026-10-03-*`), not on these bytes.
