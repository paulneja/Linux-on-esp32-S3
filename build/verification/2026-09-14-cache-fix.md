# The flash-cache fix, measured: 25 of 25 factory boots clean

DEVELOPMENT.md incident 15 -- a kernel fault in roughly one factory boot in
ten since the 0.7 release, two in ten on this branch, ten in seventeen on one
bad afternoon -- has a cause and a fix. Everything below is on the same
kernel (`xipImage` `48713c61…`), the same rootfs (`b5927369…`) and the same
`/etc` and `/home` artifacts as the 10-of-17 run, on the same board, two
hours apart. Only the firmware and the soak runner changed.

## The cause, in one paragraph

The ESP32-S3 has one flash cache for both cores. Linux reads jffs2 straight
through it and writes by IPC to core 0. After a write, ESP-IDF invalidates
the cache for the written page only if its MMU accounting knows that page
(`components/spi_flash/flash_mmap.c:355`), and it does not know any
partition Linux mapped for itself -- the boot banner says `firmware uses
entries 0..9`; Linux takes 14 and 0x54 up. So no jffs2 write ever
invalidated anything. jffs2 read stale pages back (the `crc error`s, the
scripts with syntax errors), and stale lines shared cache sets with kernel
literals (the Oops in `check_lifetime` that loaded a return address where
`jiffies_64` should have been). The soak runner made it worse by resetting
the board in the middle of `home-init`'s writes, which is what the "faults
before any process exists" were: the next boot over a half-written `/home`.

## The fix

`patches/02-firmware-network-adapter.patch`, `linux_flash.c`: after each
write or erase Linux asks for, `Cache_Invalidate_Addr(0x42000000 +
cmd->addr, cmd->size)` -- the ROM call, which takes a virtual address and
does not consult the MMU accounting that does not know the range.
`build/soak-boot.py`: `--after no_reset`, and one deliberate reset over EN
once the port is listening, so the boot observed is the first after the
write.

## Measured

| run | firmware | runner | result |
|---|---|---|---|
| 22:00, same bytes | unfixed | old (reset mid-write) | **10 FAIL** of 17 decided, 3 hung |
| 23:04, board barely warm | unfixed | new (no reset mid-write) | 4 panic, 2 hung, 2 clean of 8 |
| 23:40 | **fixed** | new | **5 PASS of 5** |
| 23:50 | **fixed** | new | **20 PASS of 20** |

The 20-round run: every round reached a login, ran `dmesg` and read
`/proc/sys/kernel/tainted` back as `0`, no `INCONCLUSIVE`. Login at
13.6-14.0 s in all twenty. Upper bound on the fault rate, one-sided 95%
over 20 decided: 14%. [`2026-09-14-cache-fix-soak.json`](2026-09-14-cache-fix-soak.json).

Row two is the runner fix on its own, and it does nothing: the fault is the
cache, not the reset. Row one to row four is the firmware fix. (It is not a
perfect isolation -- row two's runner also had the fix and row four's
firmware also had it -- but the runner alone moving nothing and the pair
moving everything leaves little for the runner to have contributed.)

## What this does and does not say

Twenty-five clean boots against ten faults in seventeen on identical bytes
is not luck; the earlier 0-of-20 of 2026-09-13 might have been, and the
record for that day says so. It is also not proof the rate is zero: 14% is
the bound twenty rounds can give, and the 2026-09-13 run got the same bound
the day before it fell over. What is different this time is that the cause
is known and the fix addresses it directly, so the next twenty are expected
to look like these, not like the ones before.

Not covered: WiFi association and traffic under the fixed firmware, the BLE
dialog, and a clean `reproduce.sh` build carrying the patch -- the firmware
measured here was built in the same container from the same tree, but not
by the full pipeline.
