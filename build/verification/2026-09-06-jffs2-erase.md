# Writes to /home collapse once jffs2 has to reclaim blocks

Board: ESP32-S3 N16R8, console over COM, `/home` is the 3.25 MiB jffs2
partition at `0xcc0000`.

## Symptom

Writing into blocks that are already clean is normal: 512 KiB takes 5 to 6
seconds. Once the filesystem has to reclaim and erase used blocks, throughput
collapses. Filling 2.25 MiB did not finish within 600 seconds. It is not a
deadlock: `/home` usage kept climbing across attempts, so the work does
progress, far too slowly to be usable.

Before this was bounded, a board left in that state stopped booting. Init ran
`home-init`, which writes to `/etc`, also jffs2 on the same chip, and the boot
never reached the login prompt.

## Which kernel

Measured on the same board and the same partition contents, filling 2.25 MiB:

| Kernel | Result |
|---|---|
| `6.11.0-forkbank` | not finished in 600 s |
| `6.11.0-nofork`, same tree, `XTENSA_NOMMU_FORK` disabled | not finished in 600 s |
| `6.11.0`, the published 0.6 release | not finished in 600 s |

**This is not a regression of this branch.** An earlier reading of it was
wrong: the first-boot difference against 0.6 has another explanation. 0.6 has
no `S06home-users`, and a factory partition is entirely `0xff`, so its first
boot only writes cleanmarkers and never has to erase a used block.

## Where it comes from

Linux does not drive the flash. The ESP-IDF firmware on the other core does,
over a shared-memory IPC. `esp32_ipc_flash_io_iram()` in
`drivers/mtd/chips/map_esp32.c` is marked `__xipram` so it runs from RAM,
disables interrupts, and busy-waits for the other core to report completion.
The kernel and the rootfs are both XIP from the same chip, so nothing else can
run during that window. Reclaim work is many such operations in sequence.

The exact cost per erase was not instrumented, and no fix for the throughput
itself is attempted here.

## What was changed

`S06home-users` now waits a bounded 45 seconds for `home-init` and lets the
boot continue regardless, so a board in this state still reaches a login
instead of becoming unusable. `web-server migrate` returns before creating its
temporary file when the configuration already points at `/home/www`, removing
a write from `/etc` on every boot.

Verified on a board whose `/home` had been left needing reclaim: login in
42.7 s, where the same state previously did not reach login in 280 s.

## Scope of the passing board suite

The 26/26 run is valid for what it covers. It never rewrites enough of
`/home` to force reclaim, so it does not exercise this path.
