# JFFS2 block erase stalls on the fork kernel

Board: ESP32-S3 N16R8, console over COM, `/home` is the 3.25 MiB jffs2
partition at `0xcc0000`.

## What was measured

| Kernel | `/home` state | Result |
|---|---|---|
| `6.11.0` (0.6 release) | erased, no cleanmarkers | `S05home: created /home/root`, login in 11.5 s |
| `6.11.0-forkbank` | erased, no cleanmarkers | no login in 280 s, stops after `Running sysctl: OK` |
| `6.11.0-forkbank` | formatted, empty | login in 18.9 s |
| `6.11.0-forkbank` | formatted, clean blocks | 512 KiB written in 5.4 to 6.1 s |
| `6.11.0-forkbank` | blocks need recycling | write never returns, over 180 s |

After the stalled write the console still echoes input but no command runs:
the shell is blocked in the kernel. Resetting does not recover; the board
stops at the same point in `S05home`. Rewriting `home.jffs2` restores it.

Same board, same partition contents, different kernel. Erasing 52 blocks
takes seconds on the stock kernel, so partition size does not explain it.

## Where it comes from

Shipping a formatted factory `/home` removes the first-boot trigger only.
Any normal use that rewrites files in `/home` eventually needs jffs2 to
recycle blocks and reaches the same stall.

`nommu_bank_switch()` runs on every context switch and copies the private
banks page by page inside `local_irq_save()`/`local_irq_restore()`, up to the
512 KiB per-fork limit. Erase completion on this memory-mapped flash and the
`jffs2_gcd_mtd` thread that `jffs2_reserve_space` waits for both need to make
progress during that window.

This explains the symptom and matches the isolation above, but causation was
not instrumented. Confirming it requires a kernel built with the copy moved
out of the interrupt-disabled window.

## Scope of the passing board suite

The 26/26 run is valid for what it covers. It never rewrites enough of
`/home` to force a block recycle, so it does not exercise this path.
